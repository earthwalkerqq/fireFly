# Анализ проекта **firefly**

Документ — результат построчного разбора всех `*.c`/`*.h`, шейдеров, `Makefile`, `.gitignore` и структуры каталога `materials/`. Бинарные данные (`materials/BLSP_256/...`) не разбирались, проверен только формат их чтения по коду.

---

## 1. Что это за проект

Интерактивный 3D-вьювер на **C11 + OpenGL 3.3 (GLFW + GLEW + cglm)**. Загружает:

- **RZP** — растровую матрицу рельефа `258 × 258` целых (с паддингом `+2` по одной оси) из файла `materials/BLSP_256/RZP/i/j`;
- **TLO** — фрагменты облака точек (триплеты `double x,y,z`) из `materials/BLSP_256/TLO_INT/i/j` — каждое имя файла кодирует индексы тайла.

После загрузки строится **триангуляция Делоне Бойера–Уотсона** (своя реализация, многопоточная через `pthread`), и поверх неё ищутся **«безопасные» связные области** — треугольники, у которых превышение точки над рельефом не более `MAX_HEIGTH = 5 м`, уклон не более `ANGLE_SLOPE = 10 %`, и контур области отстоит не ближе `RADIUS_LA = 18` от любой «опасной» границы (RLA — радиус летательного аппарата). Рендер: либо облако точек, либо каркасная сетка с подсветкой безопасных зон синим. Камера управляется WASD + Space + O/P/K/L.

Сборка — обычный `Makefile` с авто-определением macOS/Linux и `pkg-config`. Прицепленных зависимостей в каталоге `deps/` нет, триангуляция написана своя.

---

## 2. Сильные стороны

- Чёткое разделение ответственностей по модулям (`rzp`, `tlo`, `triangulation`, `findSafe`, `shader`, `common`, `main`).
- Триангуляция оформлена аккуратно: doxygen-комментарии, отделены «рабочие» структуры `bw_triangle_t/bw_edge_t` от публичных, есть распараллеливание помеченных предикатов через `pthread`, подвыборка для крупных облаков (`subsample` ≥ `MAX_TRIANG_POINTS`).
- Поиск связных областей и контуров через хеш-таблицу рёбер `O(N)` — это правильное решение, а не наивное `O(N²)`.
- Геометрия безопасных зон считается аккуратно: расстояние «треугольник — отрезок контура» с явной проверкой пересечений и попадания в треугольник.
- Шейдер с двумя режимами и явной таблицей цветов по перепаду высот.
- `Makefile` корректно отрабатывает и macOS (через `/opt/homebrew/Cellar/...`), и Linux (через `pkg-config`).

## 3. Критические баги (нужно чинить)

### 3.1. Двойной `fclose` в `getTloPoints` (`src/tlo.c:65–73`)
```c
if ((hasBeenRead = fread(buffer, 1, sizeFrgData, fd)) != sizeFrgData) {
  fprintf(stderr, "FILE %s HAS BEEN READ NOT FULL\n", fullpath);
  fclose(fd);                 // ← закрыли
  if (!hasBeenRead)
    return 0;
}
fclose(fd);                   // ← повторно закрыли при частичном чтении
return 1;
```
При **частичном** чтении (`hasBeenRead > 0 && != sizeFrgData`) файл закрывается дважды → **UB**. Аналогичная логика в `getRZPMtrx` написана корректно — посмотрите на неё как на эталон.

### 3.2. Поломанный учёт `min/max` границ облака точек (`src/tlo.c:533–538`)
```c
if ((float)x < tlo->minX) tlo->minX = (float)x;
else if ((float)x > tlo->maxX) tlo->maxX = (float)x;
```
Условия должны быть **независимыми** (`if/if`), а не `if/else if`. С `else if` при возрастающей по X последовательности `minX` не обновляется ниже первой точки нормально, но при **убывающей** последовательности всегда срабатывает первая ветка — и `maxX` навсегда остаётся равным `-FLT_MAX`. От этого зависит начальная позиция камеры: при «плохой» порядковости точек камера полетит в `-FLT_MAX/2` и сцена будет вне фрустума. Исправить на:
```c
if ((float)x < tlo->minX) tlo->minX = (float)x;
if ((float)x > tlo->maxX) tlo->maxX = (float)x;
```
То же для Y и Z.

### 3.3. Аргумент пути из `argv[1]` игнорируется для RZP (`src/main.c:209, 225`)
```c
const char *pathData = (argc > 1) ? argv[1] : PATH_DATA;
...
if (!getRZPMtrx(PATH_DATA, RZP_TILES[0], heights)) {   // ← PATH_DATA, не pathData
```
TLO потом грузится из `pathData`, а RZP — всегда из фиксированного `./materials/BLSP_256`. Любой пользовательский путь работает только наполовину.

### 3.4. Глобальная переменная объявлена в заголовке как **определение** (`include/common.h:18`)
```c
char drawMode;
```
В заголовочнике должно быть `extern char drawMode;`, а **определение** — ровно в одном `.c`. Сейчас:
- `common.h` создаёт *tentative definition* в каждом `.c`, который её включает (`main.c`, `tlo.c`, `rzp.c`);
- собирается без ошибок только потому, что линковщик GCC/Clang по умолчанию ещё допускает common-символы;
- с `-fno-common` (по умолчанию с GCC 10) проект **перестанет линковаться**.

Заодно: тип `char` неинформативен — заведите `enum DrawMode { DRAW_POINTS=1, DRAW_TRI=2 };`.

### 3.5. Утечка `vrt` при сбое внутри `loadAllTloData` (`src/tlo.c:511–515`)
```c
double* ptsFull = (double*)malloc(countPoints * 3 * sizeof(double));
if (!ptsFull) {
  fprintf(stderr, "FAILED FROM MEMORY ALLOCATE\n");
  return 0;                  // ← `vrt` (наверху) не освобождён
}
```
Чините: освобождайте `vrt` перед `return 0` или сделайте единую точку выхода через `goto fail`.

### 3.6. `TLO_TILES[128]` — переполнение глобального массива (`src/tlo.c:29, 388`)
```c
FrgIndex TLO_TILES[128];
...
TLO_TILES[(*countTlo)++] = (FrgIndex){...};
```
В `varifyTloData` нет проверки `*countTlo < 128`. Судя по `materials/BLSP_256/TLO_INT`, тайлов уже под сотню, и при росте облака переполнение приведёт к молчаливой порче памяти. Замените на динамический массив (`realloc`-стратегия).

### 3.7. Утечки GL-ресурсов в `createShader` (`src/shader.c:60–85`)
- Если один из `compileShader` вернул 0, второй (валидный) шейдер не удаляется.
- Если `glLinkProgram` упал, `shaderProg` остаётся живым, а скомпилированные шейдеры — приаттаченными.

Нужно:
```c
if (!compShaderVert || !compShaderFrag) {
  if (compShaderVert) glDeleteShader(compShaderVert);
  if (compShaderFrag) glDeleteShader(compShaderFrag);
  return 0;
}
...
if (!success) {
  glDeleteShader(compShaderVert);
  glDeleteShader(compShaderFrag);
  glDeleteProgram(shaderProg);
  return 0;
}
```

### 3.8. Окно создаётся **полноэкранным** (`src/main.c:50`)
```c
GLFWwindow *window = glfwCreateWindow(WIN_WIDTH, WIN_HEIGHT, "FireFly",
                                      glfwGetPrimaryMonitor(), NULL);
```
Четвёртый аргумент — `monitor`. Если он не `NULL`, окно создаётся **в режиме монитора** (`WIN_WIDTH×WIN_HEIGHT` будут трактоваться как видеорежим). Большинство мониторов такого режима не поддержат, и GLFW отвалится либо переключит разрешение. Если фуллскрин не нужен — передайте `NULL`.

## 4. Серьёзные замечания (потенциальные баги / плохая инженерия)

### 4.1. `memoryRealloc` нарушает контракт `realloc`
```c
void* memoryRealloc(void* ptr, size_t size) {
    void* res = realloc(ptr, size);
    if (!res) { free(ptr); ... return NULL; }
    return res;
}
```
Стандартный `realloc` при ошибке оставляет старую память валидной — пользователь сам решает, освобождать ли её. Эта обёртка **молча уничтожает данные**, что ломает идиоматику. Если хотите такое поведение — назовите функцию иначе (`memoryReallocOrFree`).

### 4.2. `getDirname` (`src/tlo.c:31–51`) хрупкая
- Не проверяет, что в пути есть **два** слеша. Если путь оканчивается на `/file`, первый цикл `for (i = len-1; path[i] != '/'; i--)` пройдёт ОК, но второй уйдёт `i = -1`, и чтение `path[i]` — UB.
- Аллоцирует строку лишь чтобы прогнать `atoi`. Парсите два индекса напрямую через `sscanf(entry->d_name, "%d", ...)` плюс «родительский каталог» — не дёргайте кучу.

### 4.3. Поиск `else if` для границ камеры в шейдере вершин — не относится; это уже отдельный вопрос.

### 4.4. `point_t::id` фактически мёртвое поле
Заполняется в `loadAllTloData` (`vrt[fragNumber].id = fragNumber`), но ни в одном месте кода больше не читается. После `subsample`/`qsort` в триангуляции значение всё равно теряет смысл. Удалите.

### 4.5. `varifyTriangles` (`src/findSafe.c:42`) — мёртвая функция
- Передаёт `countPoints = 0` в `triangulation_find_polygons`, который при таком аргументе сразу выходит.
- Сама функция помечена комментарием «not wired into rendering yet».

Либо допишите, либо удалите вместе с `findSafe.h`/`findSafe.c`. Бинарь её всё равно линкует.

### 4.6. Дублирование предиката «корректного треугольника»
`isCorrectTriangle_local` (`tlo.c:329`) и `isCorrectTriangle_cb` (`findSafe.c:20`) — почти одно и то же с разной интерпретацией `height`. Первый учитывает `p->z - p->height`, второй — только `p->height`. Поведение `findSafe` сейчас неверное (но не вызывается). Если функция активируется, появятся два расходящихся определения «безопасной зоны».

### 4.7. `tlo->totalPoints` — `GLsizei` (32-битный знаковый), а `fragNumber` — `size_t`. Молчаливое усечение для облаков > 2 млрд точек. Маловероятно на практике, но `printf("avg count poinst = %d\n", tlo->totalPoints / countTlo)` уже идёт с типом, который может стать отрицательным.

### 4.8. `glfwGetTime()` возвращает `double`, но `mainloop` сразу кастит во `float`. Для длинной сессии (часы) дельта-фрейм потеряет точность. Несущественно для геймплея, но «правильно» хранить в `double`.

### 4.9. `mainloop` зависит от `glfwGetWindowSize` **каждый кадр**. Лучше повесить callback на ресайз и кэшировать.

### 4.10. `glGetUniformLocation` зовётся **каждый кадр** (model/view/projection/aspect/render_mode/wire_override/wire_color). Это O(string-hash) на драйвере. Закэшируйте локации один раз после линковки.

### 4.11. `if (!drawTlo(tlo, shaderProg)) return;` посреди `mainloop` — на единственный кадр без points цикл выходит, окно перестаёт обновляться, но не закрывается. Лучше логировать раз и продолжать.

### 4.12. Хардкод `#define DEBUG` в `main.c`. Должно управляться через `-DDEBUG` в `Makefile` (`CFLAGS += -DDEBUG`).

### 4.13. В `keyCallback` повороты `yaw/pitch` идут на каждом GLFW-poll **без учёта `deltaTime`** — скорость поворота зависит от FPS. Скорость движения — учитывает, а скорости вращения — нет. Несимметрично.

### 4.14. Орфографические опечатки в API: `varifyTloData`/`varifyTriangles` — должно быть `verify…`; `count poinst` — `points`. Эти имена уже растеклись по нескольким файлам и хедерам, дальше править будет дороже.

### 4.15. `int heights[RZP_MATRIX_SIZE]` (`main.c:224`) — `258·258·4 ≈ 266 КБ` на стек. На macOS/Linux это пока укладывается в дефолтный 8 МБ, но решение фрагильное при росте `FRG_SIZE_*` или сборке потоком с меньшим стеком. Переведите на `malloc`/`calloc`.

### 4.16. Триангуляция ограничена `MAX_TRIANG_POINTS = 12000`. Это компромисс ради интерактивности (понимаю), но `subsample` выбирает «ближайшую к центру ячейки» точку — теряется высотный экстремум (а именно высокие препятствия важны для safety!). Подумайте над «выбираем самую высокую (`z - height`) точку в ячейке» — это даст консервативную оценку препятствий.

## 5. Архитектура и поддерживаемость

- **Глобальные переменные** (`drawMode`, `TLO_TILES`, `cameraPos/Front/Up`, `pitch`, `yaw`) разлили состояние по всему приложению. Просится `typedef struct { ... } AppState;` и передача указателя.
- **Двойной формат данных**: `getTloPoints` читает `double`, тут же конвертит во `float` и сохраняет в `point_t`. Если когда-нибудь захочется честно работать с большими сценами в мировых координатах (тысячи метров) — `float` будет терять точность; либо сразу сделайте всё `double`, либо вычитайте «центр сцены» перед кастом во `float`.
- `common.h` лежит в `include/`, но **тащит** `<cglm/cglm.h>` — то есть каждый `.c`, которому нужны только `memoryAlloc`/`memDestroy`, всё равно подтягивает 30+ заголовков cglm. Сделайте `common.h` лёгким.
- В `Makefile`:
  - нет авто-зависимостей (изменение `.h` не вызывает пересборку). Добавьте `-MMD -MP` и подгрузку `*.d`;
  - нет режима debug (`-O0 -g -fsanitize=address`) — а он бы быстро поймал баг 3.1 и 3.5;
  - `clean` не чистит `*.dSYM`, скомпилированный бинарь имеет имя `firefly`, но в репозитории остался **stale-артефакт** `build/delaunay.o` (видимо, после переименования файла);
  - `CFLAGS += $(THREAD_FLAGS)` дублируется в `LDLIBS` — на macOS оба раза не вредят, но избыточно.
- В `.gitignore` стоит `materials/BLSP_256`, но папка фактически закоммичена. Либо чистите репозиторий (`git rm --cached -r materials/BLSP_256`), либо уберите запись из `.gitignore`. Заодно: лежит `materials/.DS_Store` — мусор macOS.
- `include/.gitignore` и `src/.gitignore` пустые-ненужные.
- Лежит каталог `build/` с одним `delaunay.o` — должен быть в `.gitignore` (он там есть, но `delaunay.o` всё равно отслежен — `git ls-files`).

## 6. OpenGL и шейдеры

- `glEnable(GL_VERTEX_PROGRAM_POINT_SIZE)` есть, но `glShadeModel(GL_SMOOTH)` и `glPolygonMode(GL_FRONT_AND_BACK, GL_FILL)` — это **из старого профиля OpenGL**. В Core Profile (вы запросили `GLFW_OPENGL_CORE_PROFILE`) эти вызовы либо игнорируются, либо вызывают `GL_INVALID_ENUM`. Уберите.
- `glColorMask(...) + depth prepass + wireframe` (`drawTriangles`) — нормальный приём, но в Core Profile **`glLineWidth > 1` не гарантирован**, на macOS обычно работает только `1.0f`. Рассмотрите wide-line через геометрический шейдер или специальную сетку.
- Цветовые таблицы в `getColorPoint` написаны в диапазоне `0..255` и потом делятся на `255.0`. Дешёвый рефакторинг — записать сразу в `[0..1]`, и компилятор шейдера не делал бы лишних делений (он сделает фолдинг, но читать неудобно).
- `gl_PointSize` дискретными степенями (`if (h < 3) 2.; if (h < 4) 2.2; ...`) выглядит как «настроено вручную». Имеет смысл сделать линейную/логарифмическую функцию.
- В `mainloop` отсутствует обработка ошибок GL (`glGetError`). При разработке полезно ставить `#ifdef DEBUG` проверку после ключевых вызовов.

## 7. Многопоточность в триангуляции

- `mark_bad_triangles` корректно джойнит созданные потоки перед фолбеком на однопоточный путь.
- `triangulation_worker_count` берёт минимум из `CPU`, `TRI_MAX_WORKERS=8`, `work_items / TRI_PARALLEL_MIN_ITEMS`, чтобы не запускать 8 потоков на 100 элементов. Хорошо.
- Параллельно считается только «отмечает плохие треугольники» и «применить предикат». **Сам перебор точек, поиск контуров, hash-table — последовательны**. Это разумно для 12 000 точек, но если когда-то снимете лимит — основным боттл-неком станет линейный поиск в `toggle_boundary_edge`. Замените на хеш-таблицу рёбер при росте `N`.
- Никаких `pthread_mutex` нет — но и не нужно: каждый воркер пишет в свой кусок массива `bad[]`. Хорошо.

## 8. Поиск безопасных зон (логика)

- В `triangTlo` используется `isCorrectTriangle_local`, который отбраковывает треугольник, если **хоть одна** его точка имеет `z - height > MAX_HEIGTH`. Но дальше при выделении «безопасной» области требуется ещё `min_dist2_triangle_to_contours(...) >= aircraftR² (18²)`. Идея: «вся 18-метровая окрестность ВС должна попадать в плоский участок, не задевая препятствия». Это рабочая аппроксимация.
- Однако `min_dist2_triangle_to_contours` сравнивает только с **контуром текущей области (`pid`)**. Препятствие, расположенное **внутри** области (например, точка, помеченная неверно), учитываться не будет — потому что внутрь pid-области она не входит. Лучше считать расстояние до объединения всех «плохих» треугольников или хотя бы до всех контуров с любым `pid != current_pid`. Сейчас, если в безопасной зоне есть «дырка», она работает только если эта дырка стала отдельным контуром.
- `MAX_HEIGTH` — опечатка (`HEIGHT`), уже разъехавшаяся по коду.
- `ANGLE_SLOPE = 0.1` сравнивается с `(maxH - minH) / sqrt(minD2)` — это **tg угла наклона**, не сам угол. То есть фактически: «10 % крутизны» (а не 10 градусов). В комментарии так и написано. Чтобы не путать читателя, переименуйте константу в `SLOPE_TAN_MAX`.

## 9. Безопасность чтения с диска

- `getRZPMtrx` и `getTloPoints` верят содержимому файла. Если файл RZP короче — `int heights[RZP_MATRIX_SIZE]` останется с мусором из стека (не инициализирован).
- `varifyTloData` рекурсивно ходит по `materials/.../TLO_INT`. Если попадётся симлинк-петля, обход уйдёт в бесконечность. Лучше использовать `nftw` с `FTW_PHYS`, или хотя бы проверять `lstat`.
- `entry->d_name` сравнивается только с `.`, `..`, `info`. Если в каталоге окажется `.DS_Store`, он попытается стать тайлом → `atoi(".DS_Store") = 0` → пропустит проверку, но затем `fopen` его всё-таки прочитает и интерпретирует как `double`-ы. Реальная проблема: у вас в `materials/.DS_Store` уже лежит такой файл.

## 11. Что мне понравилось больше всего
